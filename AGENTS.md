## Staged game rebuild harness

- Two-chat ownership: the management chat owns requirements, durable rules, Notion journals and user-facing documentation. The implementation chat owns authorized code, tests, debugging and English evidence handoffs. Implementation agents must not write Notion or revise project-wide planning/rules; follow `docs/harness/ROUTING.md` for the boundary.
- Read `docs/harness/README.md`, `docs/harness/tasks.json`, and only the selected task's references before new-game work.
- Use English for internal agent prompts, repository task records, reviews, and handoffs. Git commit subjects and bodies are Korean; preserve module slugs and revision labels as specified in BRANCH_COMMITS.md. Notion is human-facing: write rich, readable Korean branch development journals under `docs/harness/NOTION_WORKFLOW.md`, not compressed agent notes. Keep app copy and final user reports Korean; avoid routine narration unless required by higher-priority instructions or a material blocker.
- Work one authorized vertical slice at a time. Do not implement the entire backlog. Google sign-in and first-login name/student-number/department are selected in docs/harness/PRODUCT_DECISIONS.md for a later slice. Firebase/provider configuration, cloud synchronization/photos and Gemini RAG remain separately gated; do not expand the active module into authentication.
- Standing authorization (2026-11-06): after the active module passes acceptance, relevant checks and independent review with no unresolved findings, management integrates it into main, verifies the integration, pushes main, records the journal and advances to the next eligible module without asking for routine merge/start approval. Follow `docs/harness/INTEGRATION.md`. Unresolved product decisions still require resolution; do not implement multiple modules at once.
- From the next module after the already-running H01, follow `docs/harness/BRANCH_COMMITS.md`: stable `<module>` (no prefix) branches and module-scoped versioned commit subjects. Do not rename branches or rewrite existing commits to retrofit this policy.
- Module branches must also be published to GitHub for teammate collaboration. Management owns normal feature-branch pushes at meaningful committed checkpoints, remote-SHA verification and main integration. Branch publication is not acceptance; keep review gates. Do not publish only a baseline branch as if implementation were uploaded, commit another owner's unfinished work, force push or mass-publish unrelated historical branches. See BRANCH_COMMITS.md.
- Keep replaceable Java/XML presentation separate from game rules, storage, clocks, and device APIs. Follow `docs/harness/UI_BOUNDARIES.md`.
- Use the requested coordinator -> Sol PM -> Terra/Luna specialist hierarchy only for bounded useful work. Read `docs/harness/ROUTING.md`; do not silently invent model IDs.
- Assign one branch/worktree and an explicit write scope per implementation task. Workers are not alone: preserve others' edits; escalate shared app-file changes through the PM to the implementation lead. Project-wide rules and scope changes belong to management; see ROUTING.md.
- New Git worktrees do not include uncommitted edits. Use the recorded reviewed baseline in the task board, checkpoint any later pre-existing app changes before branching, and never reset/stash/delete them automatically.
- A written agent profile is configuration, not evidence that the role ran. Record the actual model, base SHA, commands, outcomes, and remaining limits in each handoff.
- The management chat keeps one Notion development journal per actual branch in the existing board inside AI기반모바일프로그래밍; never create pages per task, subtask, agent or session. Follow `docs/harness/NOTION_WORKFLOW.md` and `notion.json`. Implementation chats provide evidence only. Future branches stay in main's plan until created. Internal task packets remain separate from Notion's branch-level records.
- Write the journal as an evidence-based Korean development narrative: goal, technology and rationale, implementation, observed verification/demo, real failures and attempted fixes, current limits and next step. Do not invent experiments, root causes, successes or human authorship for a convincing story.
- Keep `tasks.json`, task handoffs, and the branch journal consistent. Distinguish verified feature commits from integration into main. If Notion is unavailable, preserve a pending-sync record locally and disclose it; never claim a successful update.

## Delivered

New Java `game/sync` classes provide the scoped coordinator, immutable milestones, explicit registry, session guard and backend/store ports. The production registry starts empty. The dedicated SQLite outbox stores its local projection and pending revision in one transaction. Durable keys use project, UID, dataset, mode and building. Session generation controls in-flight ownership, so a fresh session for the original UID can resume the same row.

Firestore integration accepts an already selected instance and rejects a mismatching project. Server reads reject cached or locally pending snapshots. A per-building transaction retains the earliest intro and first accepted pass. The outbox acknowledges only a covering response for its submitted revision. A stale session cannot apply a returned snapshot. One explicit flush attempts one revision, with no app background retry loop. Retryable failures retain the revision, and permanent rejection remains visible.

No fixture/demo/practice/legacy data is promoted. Cloud pass summaries stay separate from local quiz attempt history. The implementation is additive to the existing code and has no startup wiring.

`AuthoredProgressRepository` implements the existing `ProgressRepository` and new `CommittedMilestoneSource` for one captured NORMAL building. `SQLiteAuthoredProgressStore` persists the aggregate and observed first-pass timestamp in a single transaction in `firststep-authored-gameplay.db`. When observed time falls outside sync validation, the local pass and its timestamp remain intact. `latest(scope)` reports `UnusableMilestone`, leaving existing outbox state intact.

`MilestoneReconciler.reconcile(scope)` checks eligibility and owner before reading that committed source, then rechecks ownership through the coordinator when recording to the outbox. A future host calls it after commit and on reopen. This recovers the gameplay-commit/outbox gap and makes enqueue replay idempotent. Flush remains separate.

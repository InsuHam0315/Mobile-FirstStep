# 국립군산대학교 학교생활 챗봇 설계안

기준일: 2026-11-05
상태: 사용자 요구사항과 구현 기준을 정리한 설계. 챗봇 수집기·검색·생성 API·앱 대화 화면은 아직 구현하지 않았다.

## 최신 제약: 무료 우선 및 통합 피드백 반영

2026-11-05 사용자는 Firebase와 가능한 한 유료 서비스를 쓰지 않는 구성을 선호한다고 밝혔다. 아래 기존 MySQL 구성 설명은 현재 구현 또는 이전 제안이며, 무료 우선 목표 구성은 Firebase Authentication + Cloud Firestore Spark, 기기 내 사진·Room 저장, Gemini 무료 등급 + RAG다. 실제 계정 생성·서비스 전환·결제 설정은 아직 하지 않았다.

- Google 로그인과 텍스트 기록 동기화는 Spark 무료 한도 안에서 검증한다. SMS 인증은 도입하지 않는다.
- Cloud Storage와 배포형 Cloud Functions는 Spark에서 사용할 수 없으므로 초기 구성에서 제외한다. 사진은 기기 내 파일로 저장하고 Room에서 관리한다. 다른 기기로 사진이 자동 복원되거나 삭제 후 서버에서 복구된다고 안내하지 않는다. 사진을 Base64로 Firestore에 밀어 넣는 우회는 사용하지 않는다.
- Firestore Standard 무료 기준: 저장 1 GiB, 읽기 하루 50,000회, 쓰기 하루 20,000회. 프로젝트 단위 한도이며 사용자 수 보장이 아니다. 실시간 리스너 남용을 피하고 완료·변경 시 저장, 목록 페이지 처리와 캐시를 적용한다.
- Gemini 공식 가격표에 File Search의 Free Tier가 무료로 표시되어 있다. 다만 모델·계정별 실제 제공 여부와 할당량은 AI Studio에서 검증해야 한다. File Search 용량 안내의 Free 한도는 1 GB이며 원문과 색인 크기를 함께 고려한다. 무료 호출 제한 시 무한 재시도하지 않고 공식 자료 검색 결과·FAQ를 제공한다.
- 무료 Gemini에 제공하는 내용은 공개 학교 자료와 필요한 질문으로 제한한다. 무료 등급은 제품 개선을 위한 데이터 사용 조건이 있으므로 학생 개인정보·민감한 상담 내용·개인 기록을 전송하지 않는 설계가 필요하다.
- 개발·수업 시연의 챗봇 중계 서버와 자료 갱신 도구는 팀 PC의 FastAPI로 실행할 수 있다. PC 전원과 네트워크 연결이 필요하며 학교 전체에 상시 배포하는 서버를 확보한 것은 아니다. Gemini 키를 APK에 넣어 서버를 생략하지 않는다.
- Firebase와 Gemini의 유료 등급 전환·결제 계정 연결을 자동으로 진행하지 않는다. 계정이 이미 유료 등급이면 무료라고 가정하지 않고 실제 설정부터 확인한다.

첨부된 통합 피드백은 전달된 의견과 검토안을 모은 자료다. 특히 시설 탐방 중심의 범위 유지, 건물 조사→활동→기능 선정 순서를 개발 판단에 반영한다. 학교 전반 질의응답 목표는 유지하되 챗봇 확대가 대표 건물 미션 구현·검증을 대체하지 않는다. 5건물 최종 목록은 미확정이며 기존 4건물·5시설 제안을 확정 기획으로 설명하지 않는다.

근거: [Firebase 가격표](https://firebase.google.com/pricing), [Gemini 가격표](https://ai.google.dev/gemini-api/docs/pricing), [Gemini 한도](https://ai.google.dev/gemini-api/docs/rate-limits), [File Search](https://ai.google.dev/gemini-api/docs/file-search).

## 목표

신입생과 복학생이 국립군산대학교 생활 전반을 자연어로 질문하고, 확인 가능한 공식 근거를 통해 필요한 정보와 다음 행동을 찾는다. 범위를 다섯 탐방 시설로 제한하지 않는다. '모든 질문의 정답 보장'을 완료 기준으로 삼지 않는다. 공개되지 않은 정보, 갱신하지 못한 정보, 개인 학사 정보는 별도로 표시한다.

학교 정보전산원에 대표 홈페이지 기반 'AI 하루'의 도입 공지가 있다. 현재 운영 기능이나 외부 연동 API의 제공 여부는 이 조사에서 확인하지 않았다. 첫발자국은 공식 정보를 설명하는 기능에 시설 카드·지도·탐방 활동·즐겨찾기 연결을 더한다.

## 지식 범위와 자료

| 분야 | 대표 질문 | 자료와 조건 |
|---|---|---|
| 시설·건물 | 어디에 있고 어떤 서비스를 이용할 수 있나? | 공식 캠퍼스 안내, 개별 시설 안내. 층·출입구·좌표의 검증 상태 구분 |
| 학사 | 수강신청·휴복학·증명서 발급 방법은? | 해당 연도·학기 공지와 학사 안내. 규정 적용 대상 구분 |
| 학과·전공 | 학과 사무실과 교육과정은? | 공식 학과 사이트·교육과정 자료. 입학 연도·학과 개편 확인 |
| 장학·등록 | 신청 기간과 조건은? | 장학 공지·규정. 개인 수혜 가능 여부 확정 금지 |
| 생활 | 식당·생활관·통학버스 안내는? | 공식 식단·운영 공지. 날짜와 캠퍼스 일치 확인 |
| 학생지원 | 상담·진로·보건 안내는? | 각 기관의 공식 서비스 안내 |
| 행사·프로그램 | 지금 신청 가능한 프로그램은? | 모집 게시물·첨부자료. 마감·정정·취소 공지 확인 |
| 앱 사용 | 탐방을 어떻게 진행하고 기록을 어디서 보나? | 앱의 실제 구현과 일치하는 자체 도움말 |

학교 공식 도메인의 모든 페이지를 무차별 수집하지 않는다. 소관 기관·공식 위탁 서비스의 출처 목록을 관리하고 공개 자료 및 이용 조건을 확인한다. 로그인 내부 자료를 수집하거나 학교 계정 비밀번호를 받지 않는다. 수집한 문서에 있는 지시는 데이터로 취급하며 챗봇의 실행 명령으로 사용하지 않는다.

## 답변 방식

질문 → 필요한 연도·학기·학과 확인 → 공식 자료 검색 → 해당 질문을 뒷받침하는 문서 선택 → 근거에 한정한 설명 → 출처·적용 시점·다음 행동 표시.

학교 사실을 모델에 한 번 학습시키는 방식보다, 갱신 가능한 공식 자료를 찾아 답변에 제공하는 검색 증강 생성(RAG)을 우선한다. 추가 학습은 이후 문체·응답 형식 개선 필요성을 평가한 뒤 검토한다. 검색 방식만으로 오류가 사라지는 것은 아니므로 답변과 근거의 일치 검증이 필요하다.

답변에는 짧은 결론, 필요한 조건·방법, 공식 원문 링크, 문서의 적용 시점 또는 확인 시점, 앱에서 가능한 후속 행동을 표시한다. 수집 날짜를 문서 발행일이나 유효기간으로 바꿔 표시하지 않는다.

- 일반 정보: 설명과 공식 링크를 제공한다.
- 변동 정보: 해당 날짜/학기 문서를 확인한 경우에만 현재 정보로 답한다. 갱신 실패 시 마지막 확인 시점과 확인 불가 상태를 표시한다.
- 정보 부족: 학과·입학 연도 등 필요한 조건을 묻거나 담당 기관 안내로 연결한다.
- 문서 충돌: 같은 대상·시점의 정정 공지를 우선 검토하고 해결되지 않으면 상충 사실을 알린다.
- 개인 정보: 개인 성적·시간표·등록·장학 심사 결과는 공개 문서로 알 수 없다. 학교가 허용한 인증·API 연계가 별도로 필요하다. Google 로그인만으로 조회할 수 없다.

시설 연결은 확인된 시설 ID로만 처리한다. 지도에는 검증된 위치만 연결하며 챗봇이 생성한 좌표를 사용하지 않는다. 예약·발급·신청은 공식 안내 링크 연결과 실제 처리 완료를 구분한다.

## 앱과 서버 구성 제안

- 기존 Android Java/XML 앱에 대화 화면, 출처 보기, 시설 카드 연결을 추가한다.
- 기존 FastAPI 서버에 수집·검색·답변 API를 분리한다. 모델 API 키는 APK에 넣지 않는다.
- MySQL에는 자료 URL·제목·본문 버전·문서 시점·수집 시점·유효기간·공개 상태와 검색 결과의 문서 ID를 관리한다. 검색 색인은 한국어 질문 평가 후 방식을 선택한다.
- 공지·식단 등 변동 자료와 시설 소개·규정의 갱신 주기를 따로 설정하고, 갱신 오류·삭제·정정 문서를 추적한다. 아직 실시간 갱신 기능은 없다.
- 대화 이력을 장기 저장할지는 최소 수집 원칙과 삭제 기능을 포함해 별도로 정한다. 사용자 개인 진행 기록은 본인 계정 범위에서만 조회한다.

## 단계별 개발과 검증

1. 시설·도서관·증명발급·학생지원의 공식 자료 목록과 검색용 문서 구조를 만든다.
2. 출처가 붙는 질의응답과 정보 부족 응답을 구현하고 실제 질문으로 검증한다.
3. 학사·학과·장학·생활관으로 범위를 확대하며 연도·학기 구분을 적용한다.
4. 갱신 주기가 짧은 공지·식단·일정의 수집과 만료 처리를 검증한다.
5. 시설 카드·지도·즐겨찾기·미션으로 이어지는 앱 흐름을 연결한다.

검증 질문은 답할 수 있는 질문뿐 아니라 잘못된 전제, 존재하지 않는 시설, 오래된 마감일, 학과가 빠진 졸업 조건, 자료 충돌, 개인 성적 요청, 자료 속 악의적 지시를 포함한다. 답변 정답률·출처 일치·시점 정확성·답변 보류의 적절성을 분리해 기록한다. 측정 전 수치를 성능으로 제시하지 않는다.

생성형 AI 서비스는 사용자 제안에 따라 **Gemini API + RAG**를 기본 방향으로 정한다. 초기 검색 구현은 Gemini File Search를 우선 검토한다. 공식 문서상 문서 분할·색인·검색과 인용 정보를 지원하므로 별도 벡터 DB를 바로 도입하지 않고 검증할 수 있다. 정확한 모델은 사용 가능한 모델·한국어 평가·비용을 확인한 뒤 설정값으로 관리한다.

제안 구조는 Android 앱 → 기존 FastAPI 서버 → Gemini File Search를 통한 문서 검색 및 Gemini 답변 → 출처 검증·시설 ID 연결 → 앱 표시다. MySQL은 기존 계정·진행 기록과 문서 원문 URL·버전·시점 관리를 계속 맡는다. 인용 문서 ID를 서버에 저장된 공식 원문 URL과 연결하며 모델이 임의로 생성한 링크를 출처로 쓰지 않는다.

File Search는 학교 웹사이트를 자동으로 계속 수집·갱신하는 기능이 아니다. 공식 자료 수집, 변경 감지, 새 버전 반영, 폐기 문서 삭제, 학기·날짜 필터는 별도로 구현해야 한다. 실제 API 키·사용 한도·비용 설정과 서비스 연결은 아직 확인하지 않았다. 현재 저장소에는 이 챗봇의 모델 연결이나 학교 전체 자료 수집 완료를 뒷받침하는 구현이 없다.

# 첫발자국 · 스냅덱 중간발표 제작 프롬프트

사용 방법: Snapdeck에서 PPT 16:9, 총 14장을 선택하고 아래 '입력할 프롬프트' 내용을 붙여 넣는다. 스타일 선택에 Standard가 있으면 이를 우선 선택하고, 밝은 배경과 단순한 도형을 사용하는 테마를 고른다. 메뉴 명칭은 현재 서비스 화면을 따른다. 현재 단계에서는 제목·핵심 내용·화면 배치를 채운 14장 구성안을 작성한다. 사용자가 실제 구성안을 검토하고 승인하기 전에는 최종 제작을 진행하지 않는다.

목표: 프로젝트 목적은 짧게 설명하고 실제 구현, 동작 흐름, 개발 과정에서 해결한 문제, 에뮬레이터 검증 근거를 중심으로 발표한다. 아래 승인된 목차와 장 순서를 유지하고, 구성안에 대한 사용자 검토 후 최종 PPT 제작 단계로 넘어간다.

---

## 입력할 프롬프트

Snapdeck으로 대학교 AI기반모바일프로그래밍 수업의 중간발표 자료를 제작해줘. 프로젝트 이름은 '첫발자국'이고, 국립군산대학교 캠퍼스 탐방 Android 앱이다. 한국어, 16:9, 표지 포함 정확히 14장으로 구성해줘. 2번 목차와 마지막 14번 'Thank You / Q&A' 장을 반드시 포함하고, 아래 구성 외의 장은 추가하지 말아줘. 각 장의 제목과 순서는 아래 승인된 구성을 그대로 따라줘. 먼저 14장의 제목·핵심 내용·화면 배치를 담은 구성안을 보여 주고, 사용자 검토와 승인 전에는 최종 제작하지 말아줘.

### 발표의 목적과 핵심 메시지

교수님과 수강생에게 '제안했던 캠퍼스 탐방 경험을 실제 Android 앱의 5개 미션, 시설 질문, 저장, 도감까지 연결했고 에뮬레이터로 통합 검증했다'는 사실을 보여 주는 발표다. 구현 결과와 그 근거에 가장 큰 비중을 두고, 사용자가 하는 행동과 이를 처리하는 기술을 연결해서 설명해줘.

주요 사용자는 신입생이다. 목적은 낯선 캠퍼스의 시설 위치와 용도를 직접 탐방하며 익히게 하는 것이다. 효과를 측정한 사용자 실험은 아직 없으므로 학습 효과가 입증됐다는 표현은 쓰지 않는다.

초기 제안의 6개 장소·10개 미션 대신 교수 피드백 반영 기획서의 5개 장소·단일 이야기로 개발했다. 아직 시설명·출입구·좌표는 현장 확인 전 후보이며 미션 좌표는 비워 둔 상태다. 지도 바탕은 표시되지만 미검증 미션 지점을 실제 방문 좌표처럼 표시하지 않는다.

중간발표는 Android Studio의 'FirstStep API 35 QA' 에뮬레이터만 사용한다. 실기기 시연은 하지 않는다. 사진은 가상 카메라로 촬영하고, 발견은 일반 카드, 센서 행동은 길게 누르기 대체, 음성 답변은 직접 입력으로 시연한다. 대체 경로로 검증한 사실을 실제 AR·센서·음성인식 성공이라고 표현하지 않는다.

### 디자인

- 제안발표와의 연속성을 위해 밝은 아이보리 배경 #FAF7EF, 짙은 남색 제목·본문 #1E2B39, 분홍색 번호·포인트를 기본으로 사용한다. 실제 앱 캡처의 테라코타 #AB5336는 그대로 유지하되 슬라이드 전체의 분홍색 포인트와 혼동하지 않는다.
- 한글 가독성이 좋은 고딕체 한 종류를 사용하고, 제목은 30~36pt, 본문은 20~24pt 수준으로 구성한다. 내용이 많으면 문장을 줄이고 글자를 지나치게 작게 만들지 않는다.
- 한 장에 핵심 메시지 하나. 본문은 짧은 문장 3~4개 또는 간결한 표·흐름도로 표현한다. 긴 설명은 가능한 경우 발표자 노트로 분리한다.
- 구현 화면은 실제 에뮬레이터 캡처를 크게 배치한다. 제공되지 않은 앱 화면이나 테스트 결과를 AI 이미지로 만들어 넣지 않는다. 이미지가 없으면 '실제 화면 삽입 예정: 코스/촬영/도감'처럼 교체 가능한 영역으로 남긴다.
- 복잡한 스마트폰 목업, 장식용 3D 이미지, 과도한 그라데이션은 사용하지 않는다. 화면 캡처에는 단순한 테두리만 사용한다.
- 구조는 화살표와 편집 가능한 도형, 비교는 편집 가능한 표를 사용한다. 모든 장을 같은 카드 배열로 반복하지 않는다.
- 지도 캡처의 OpenStreetMap 출처 표시는 자르지 않는다. 미확인 좌표와 경로선을 임의로 추가하지 않는다.

### 슬라이드별 내용

1. 표지 — 첫발자국
   - 제목: '첫발자국 — 캠퍼스 탐방 앱 중간 구현 결과'.
   - 부제: '다섯 장소의 기억을 모으며 캠퍼스를 알아가는 Android 앱'.
   - 수업명: AI기반모바일프로그래밍. 발표일: 2026년 11월 3일.
   - 팀명: 뉴비킬러. 팀원: 유혜나 · 최동혁 · 함인수.
   - 소속: 국립군산대학교 소프트웨어학과.
   - 실제 홈 화면 한 장과 제목 중심의 여백 있는 표지.

2. 목차
   - 제안발표 PDF처럼 아이보리 배경, 짙은 남색 제목, 분홍색의 큰 두 자리 번호를 사용한다.
   - 왼쪽 약 1/3에는 실제 앱 화면 한 장을 크게 배치하고, 오른쪽에는 다음 여섯 항목을 2열×3행으로 정렬한다. 이미지가 제공되지 않았으면 교체 가능한 실제 화면 자리만 둔다.
   - 01 프로젝트 개요 (3장).
   - 02 개발 목표 및 진행 현황 (4~5장).
   - 03 주요 기능 구현 (6~9장).
   - 04 앱 시연 (10장).
   - 05 검증 결과 및 개선 사항 (11~12장).
   - 06 향후 개발 계획 (13장).
   - 여섯 항목의 이름과 순서를 그대로 유지한다. 제안발표 PDF의 기존 01~09 항목은 복사하지 않는다.

3. 프로젝트 개요
   - 대상: 캠퍼스 시설이 낯선 신입생.
   - 목표: 시설의 위치와 용도를 직접 탐방하는 경험으로 익히기.
   - 방식: 장소 확인 → 행동 미션 → 시설 질문 → 도감 기록.
   - 네 단계 흐름을 크게 보여 주고 프로젝트 목적을 간결하게 설명한다. 학습 효과가 실험으로 입증됐다고 표현하지 않는다.

4. 개발 목표 및 진행 현황
   - 수정 기획서의 목표: 5개 장소·단일 이야기, 미션 수행과 시설 안내·저장을 하나의 앱 흐름으로 연결.
   - 화면/전환, 지도·GPS, AR·카드 발견, 사진·센서·음성, 저장·도감·엔딩을 표로 정리한다.
   - 표의 열은 '개발 목표 / 현재 구현 / 확인한 범위'로 구성한다. 구현과 검증을 같은 완료 표시로 합치지 않는다.
   - 에뮬레이터에서는 5미션의 대체 입력 경로와 저장·복원을 확인했다. GPS·AR·센서의 실제 캠퍼스·실기기 검증과 시설 좌표 실측은 남아 있다.
   - 완료율 퍼센트나 팀원별 기여율은 만들지 않는다.

5. 전체 이용 흐름
   - 닉네임 → 코스 → 기억 발견 → 이야기 → 행동 미션 → 시설 질문 → 저장 → 도감/다음 장소.
   - 저장된 선행 미션에 따라 다음 미션이 열리고, 5개 기억을 모두 모으면 마지막 탐방 기록 화면으로 연결된다.
   - 실제 코스·미션·도감 캡처 3개와 화살표로 사용자 동선을 보여 준다.
   - 위치 확인을 건너뛰는 테스트 모드와 실제 현장 모드의 기록이 분리된다는 점을 짧게 표시한다.

6. 앱 구조와 기술 구성
   - Java/XML: 화면과 화면 전환.
   - CameraX·ARCore·위치 API·센서·TTS/음성 서비스: 기기 입력과 안내 연결.
   - 판정 로직: 시설 질문의 정답, 센서 유지 시간, 도착 조건, 선행 미션 확인.
   - Room: 완료 기록과 사진 경로. 로컬 체크포인트: 미완료 단계와 입력 복원.
   - 화면 → 입력·판정 → 저장의 관계를 단순 구조도로 표현한다. 서버·클라우드 DB·로그인·AI 추론 서버는 추가하지 않는다. 지도와 시스템 음성 서비스는 외부 네트워크를 사용할 수 있다.

7. 지도와 기억 발견 구현
   - 지도: OpenStreetMap 기반 캠퍼스 주변 지도, 확대·축소·이동. 지도 출처 표시는 자르지 않는다.
   - GPS: 위치의 정확도·최신성·체류 조건으로 도착 판정. 좌표가 실측·검증되지 않은 장소의 현장 시작은 차단한다.
   - AR: ARCore 평면 인식, 앵커 배치·선택 코드 구현. 미지원 환경에는 일반 카드(CARD) 발견 경로를 제공한다.
   - 지도와 기억 발견의 실제 화면을 배치한다. 이번 시연은 위치 확인을 건너뛰는 테스트 모드와 CARD를 사용하며, 현장 GPS와 AR 실기기 추적은 미검증이라고 표시한다.

8. 사진·센서·음성 미션 구현
   - 사진: CameraX 촬영 → 미리보기 → 재촬영 또는 확인 → 시설 질문. 가상 카메라 캡처임을 표시하며 건물 자동 인식 기능으로 설명하지 않는다.
   - 표의 열: '미션 / 구현한 입력 / 이번 에뮬 시연 방식'. 사진은 가상 카메라, 조도 가림·회복은 HOLD(3초 길게 누르기), 생활 음성/텍스트 정답은 TYPED(직접 입력), 방향 유지와 움직임 5회 판정은 HOLD로 구분한다.
   - TTS 안내, 조도 판정, 방향 유지, 중력을 분리한 움직임 판정이 구현돼 있음을 설명하되 이번 발표에서 실제 센서·음성인식 성공을 검증한 것처럼 표현하지 않는다.
   - 촬영 또는 미션 화면을 크게 두고 표와 연결한다. 각 대체 조작은 실제 입력 완료와 구분해 기록한다.

9. 진행 저장과 시설 도감 구현
   - Room에 모드·미션별 완료 기록, 발견 방식, 실제 입력/대체 조작 방식, 사진 경로를 저장한다. 저장 성공 후에 완료 화면을 표시한다.
   - 테스트 기록과 현장 기록을 분리하고, 선행 미션과 중복 완료를 확인해 같은 미션의 보상을 중복 지급하지 않는다.
   - 시설 도감에서는 기본 시설 안내와 검색을 제공하고, 완료 후에는 촬영 사진과 탐방 기록을 다시 볼 수 있다.
   - 화면 재생성 시 사진 확인 단계·입력한 글을 복원하며 센서 측정은 다시 시작한다. 저장 중 복원에서는 실제 DB 완료 여부를 먼저 확인한다.
   - 실제 도감·검색 화면과 '미션 완료 → 저장 확인 → 도감 기록' 흐름을 보여 준다. 모든 강제 종료 상황을 검증했다고 표현하지 않는다.

10. 앱 시연
   - 시연 전용 장. 실제 실행 화면 또는 제공된 녹화 영상을 위한 큰 영역을 둔다. 제공되지 않은 영상은 자동 생성하지 않는다.
   - 추천 시연: 테스트 모드 시작 → CARD 발견 → 가상 카메라 사진 미션 → 시설 질문 → 완료·도감 → 앱 재실행 후 기록 유지.
   - 다른 미션과 엔딩은 짧은 화면 전환 또는 캡처로 보충한다. 전체 5개 미션을 모두 실시간으로 수행할 필요는 없다.
   - 팀원 모두 iPhone 사용자이므로 중간발표의 검증·시연 환경은 Android 에뮬레이터로 통일한다. 센서는 HOLD, 음성 답변은 TYPED로 시연한다.

11. 검증 결과
   - 단위 검사 34개 통과, 에뮬레이터 기기 검사 4개 통과, APK 빌드 성공.
   - 4개 기기 검사는 기본 패키지 1개, 5미션 전체 흐름·화면 복원, 미완료 사진 정리·모드 분리, 이전 DB의 데이터 유지 검사다.
   - Android Lint: 오류 0개, 경고 78개. 오류·경고가 모두 없다고 표현하지 않는다.
   - '검사 항목 / 결과 / 확인 범위' 표로 보여 준다. 구현 기능 수와 테스트 개수를 혼합하거나 같은 검사를 재실행한 횟수를 별도 검사로 더하지 않는다.
   - 검증 범위는 API 35 에뮬레이터와 자동 검사다. 모든 기기에서의 동작이나 실기기 GPS·AR·센서 성능을 보장하지 않는다.

12. 개발 중 문제와 개선
   - '문제 / 개선 / 확인한 결과'의 전후 비교표로 구성한다.
   - 저장 전 완료 표시 위험 → 저장 성공 후 완료 표시 → 저장과 보상의 순서 일치.
   - 복원 중 완료 사진을 임시 사진으로 잘못 삭제할 위험 → DB의 사진 소유권 확인 → 저장된 사진을 보존하며 미완료 사진을 정리.
   - 화면 재생성 시 미완료 단계·입력 유실 → 체크포인트와 DB 완료 여부 대조 → 사진 확인·텍스트 입력 복원, 센서 측정 재시작.
   - 실제 구현과 검사에서 확인한 개선만 적는다. 측정하지 않은 성능 향상률, 오류 감소율이나 모든 예외 상황 해결 주장은 넣지 않는다.

13. 향후 계획
   - 현재: 5미션·저장·도감·엔딩 연결과 에뮬레이터 통합 검증 완료.
   - 다음: 실제 시설명·출입구·좌표 실측 및 확인 → 확보 가능한 Android 기기에서 AR/GPS/센서 확인 → 사용자 피드백과 화면 개선 → 최종발표 준비.
   - 중간발표 11월 3일, 최종발표 12월 1일을 표시하되 현장 검증 날짜나 기기 대여가 확정됐다고 만들지 않는다.
   - 정리 문장: '핵심 탐방 흐름을 구현했고, 다음 단계에서 실제 캠퍼스 환경에 맞춰 검증합니다.'

14. Thank You / Q&A
   - 중앙에 'Thank You'와 'Q&A'를 크게 배치하고, '감사합니다. 질문해 주세요.'를 짧게 덧붙인다.
   - 하단에 '첫발자국 · 뉴비킬러'와 '유혜나 · 최동혁 · 함인수'를 작게 배치한다.
   - 제안발표와 같은 아이보리·남색·분홍색 포인트와 충분한 여백을 사용한다.
   - 기대효과와 합치지 않는 독립된 마지막 장으로 구성한다. 새로운 구현 성과나 검증 수치는 추가하지 않는다.

### 사실을 유지하는 규칙

위 내용만 근거로 작성한다. 제안발표 PDF의 역할분담은 당시의 계획이므로 현재의 실제 기여나 팀원별 기여율로 바꾸어 설명하지 않는다. 설문 수치, 만족도, 사용자 수, 팀원별 기여율, 성능 향상률, 완료율, 현장 사진, 실제 검증 좌표는 만들어 넣지 않는다. 수업 이름에 AI가 포함돼 있어도 앱에 생성형 AI나 이미지 인식 기능을 추가해 설명하지 않는다. 제공되지 않은 실제 화면·영상은 교체 가능한 자리로 둔다. 발표자 노트 기능이 있다면 각 장에 2~3문장의 설명을 추가하되 화면에는 긴 문단을 넣지 않는다.

최종 제작 전에 반드시 14장의 제목·핵심 내용·화면 배치를 담은 구성안을 먼저 보여 줘. 사용자가 이 구성안을 검토하고 승인할 때까지 최종 제작은 진행하지 말아줘. 핵심 구현 설명이 빠지거나 미검증 내용을 완료로 바꾼 부분이 없는지 검토할 수 있게 해줘.

## 생성 전후 확인

- 정확히 14장이며 승인된 제목과 순서, 목차 6개 항목, 마지막 14번 Thank You / Q&A를 유지했는지 확인한다.
- 실제 구성안을 사용자가 검토·승인한 후에만 최종 제작한다.
- 수정 기획서의 5개 장소 기준과 34개 단위 검사·4개 기기 검사 수치를 유지했는지 확인한다.
- 실제 앱 캡처 대신 그럴듯한 가짜 화면이 들어가지 않았는지 확인한다.
- 구현 완료 / 에뮬레이터 검증 / 실기기·현장 미검증을 구분했는지 확인한다.
- 센서 대체 조작을 실제 센서 성공으로 표현하지 않았는지 확인한다.
- 사진 미션이 자동 건물 인식으로 바뀌지 않았는지 확인한다.
- 발표용 실제 영상과 화면 캡처를 삽입한 후 글자 크기·줄바꿈·지도 출처를 확인한다.
- 내보낸 PPTX를 발표 PC에서 열어 폰트·이미지·영상 재생을 확인한다.
